11. **[Audit kecacatan logika + Batch 1 — v1.4.2]** User meminta: "implementasikan semua fitur TxtPad+ hingga matang" + "audit semua kecacatan logika". Seluruh 17 file `.kt` ditelusuri manual dan fitur TxtPad+ asli diriset dari Play Store/ulasan pengguna sebelum mulai kerja (bukan tebakan). Temuan & disepakati: kerjakan berurutan per batch (bukan sekaligus), tema default TETAP gelap. Batch 1 = perbaikan bug saja:
    - **Bug nyata (diperbaiki):** `RegexUtils.regexDispatcher` sebelumnya `Dispatchers.Default.limitedParallelism(1)` — 1 thread dipakai ulang selamanya. Karena mesin regex JVM/Android tidak responsif terhadap cancellation di tengah catastrophic backtracking, thread yang timeout tetap jalan di background (ini SUDAH didokumentasikan sejak awal) — tapi karena cuma 1 thread yang di-reuse, itu berarti SATU pola regex bermasalah memblokir SEMUA permintaan Cari & Ganti Regex berikutnya selamanya (timeout terus tanpa pernah benar-benar jalan) sampai app di-restart — ini bug nyata yang belum tercatat sebelumnya, bukan cuma keterbatasan. Diganti ke `Executors.newCachedThreadPool()` — tetap terisolasi dari `Dispatchers.Default`, tapi thread yang macet ditinggalkan sendirian tanpa memblokir panggilan berikutnya.
    - **Bug nyata (diperbaiki):** `BottomFileBar` — item menu dengan `available=false` ("Segera Hadir") sebelumnya tetap memanggil `onClick()` walau tidak ada guard (untungnya belum bermanifestasi karena semua item saat ini `available=true`). Ditambah `enabled = item.available` pada `DropdownMenuItem` + guard eksplisit di dalam `onClick`.
    - **Ditinjau, SENGAJA TIDAK diubah:** `ExternalFileUtils.localNameFor` pakai hash 32-bit (`String.hashCode()`) dari Uri — risiko tabrakan kecil tapi ada. Sempat diganti ke SHA-256 lalu **dibatalkan**: mengganti algoritma hash membuat berkas yang sudah diimpor sebelumnya (nama lokal format lama) tidak lagi ter-mapping ke salinan lokalnya sendiri saat dibuka ulang lewat "Buka Dengan" — menghasilkan duplikat nyata bagi pengguna lama. Untuk risiko tabrakan 32-bit yang di praktik penggunaan nyata nyaris tidak pernah terjadi, regresi itu tidak sepadan — dibiarkan seperti semula, dicatat sebagai keterbatasan yang diterima.
    - **Belum disentuh (menunggu Batch 2 & 3):** semua fitur tampilan (font, tema) dan Info Berkas (word/char count) — sengaja tidak dicampur dengan perbaikan bug di batch yang sama.

  - **Akar masalah simbol acak, sebelum fitur ini ada:** app sama sekali belum punya kemampuan membuka ZIP — `FileUtils.readFile` (jalur baca semua berkas lokal biasa) juga hard-code UTF-8, jadi berkas apa pun (di dalam atau di luar ZIP) yang encoding aslinya bukan UTF-8 (mis. Windows-1252/ANSI dari Notepad lama) akan tampil sebagai simbol acak kalau dipaksa dekode UTF-8.
  - **Implementasi:**
    * `util/ZipUtils.kt` (baru): `listTextEntries` (daftar entri `.txt`/`.md`), `readEntryText` (baca 1 entri, batas 2MB sama seperti `FileUtils.readFile`), `importEntryToNotes` (salin ke `notesDir` dengan nama deterministik dari hash nama-ZIP+nama-entri — pola sama seperti `ExternalFileUtils.localNameFor`, supaya entri yang sama dibuka berulang tetap 1 salinan, bukan duplikat).
    * **Deteksi encoding (bagian penting):** `ZipUtils.decodeText` TIDAK memaksa UTF-8 seperti `FileUtils.readFile` — cek BOM UTF-8/UTF-16 dulu, lalu coba dekode UTF-8 ketat (`CodingErrorAction.REPORT`, gagal kalau ada byte tak valid, bukan diam-diam diganti), baru fallback ke Windows-1252 (superset ISO-8859-1, setiap byte 0x00–0xFF selalu valid didekode olehnya, jadi jaring pengaman terakhir yang wajar).
    * `ui/ZipContentsScreen.kt` (baru): daftar entri (nama + ukuran), ketuk untuk impor+buka. Bukan pengelola arsip umum (tidak ada ekstrak-semua/hapus/kompresi ulang) — sengaja dipersempit sesuai kebutuhan spesifik yang diminta (baca teks di dalam ZIP), bukan reimplementasi file manager.
    * `AndroidManifest.xml` (partial edit): tambah pola nama berkas `.zip` ke intent-filter fallback yang sudah ada (pola sama seperti `.txt`/`.md`) + 2 intent-filter baru khusus MIME (`application/zip`, `application/x-zip-compressed`) karena banyak file manager mengenali MIME zip dengan benar (beda dari `.md` yang MIME-nya sering tidak konsisten).
    * `MainActivity.kt` (partial edit): di `LaunchedEffect` penerima Intent VIEW/EDIT, ditambah percabangan deteksi ZIP (dari MIME atau nama berkas) SEBELUM jalur impor teks lama — kalau ZIP, disalin ke `context.cacheDir/zip-import/` (bukan `filesDir`, karena sifatnya sementara/bukan data pengguna) lalu ditampilkan lewat `ZipContentsScreen`; kalau bukan ZIP, jalur `ExternalFileUtils.importFromUri` yang sudah ada berjalan **persis seperti sebelumnya, tidak diubah sama sekali**.
  - **Sengaja TIDAK dikerjakan (di luar scope permintaan ini, dicatat supaya tidak dianggap luput):** `FileUtils.readFile` untuk berkas `.txt`/`.md` lokal biasa (bukan dari ZIP) TETAP hard-code UTF-8 — menyentuhnya berarti mengubah jalur baca/tulis inti yang dipakai semua fitur lain (undo/redo, auto-save, regex, dst.), berisiko regresi jauh lebih luas daripada manfaat untuk permintaan spesifik "baca ZIP" ini. Kalau ternyata berkas `.txt` biasa (bukan dari ZIP) juga menampilkan simbol acak, itu perlu instruksi terpisah sebelum jalur inti disentuh.
  - **Asumsi teknis:** tidak ada dependency baru ditambahkan (`java.util.zip.ZipFile` bawaan JDK/Android). Batas ukuran entri 2MB disamakan dengan batas `FileUtils.readFile` yang sudah ada, bukan angka baru.
  - **Circuit breaker file:** 20 file lama (setelah insiden #14), +2 file baru (`ZipUtils.kt`, `ZipContentsScreen.kt`) = 22 total — bukan regresi.
  - **Verifikasi:** tidak ada toolchain Gradle/Android SDK di lingkungan pembuatan ini untuk build asli — verifikasi lewat pengecekan keseimbangan kurung otomatis (seimbang di 3 file yang disentuh: `MainActivity.kt`, `ZipUtils.kt`, `ZipContentsScreen.kt`), validasi XML well-formed untuk `AndroidManifest.xml`, dan penelusuran manual bahwa import baru (`ZipUtils`, `ZipContentsScreen`) benar dan konsisten dipakai.

    - **Kenapa selama ini belum pernah bermasalah:** setiap ZIP yang dikirim AI sejauh ini SELALU menyertakan `.gitignore` dan `.github/` di dalamnya, sehingga langsung dipulihkan oleh `unzip -o` sesaat setelah dihapus — totalnya tidak ada file yang benar-benar hilang secara permanen (diverifikasi ulang untuk ZIP v1.6.1: `.gitignore` & `.github/workflows/build.yml` dikonfirmasi ada di dalam arsip).
    - **Risiko nyata kalau lalai:** kalau SATU KALI SAJA AI mengirim ZIP yang tidak menyertakan dotfile (mis. karena tool pembuat ZIP di sisi AI/perangkat user default menyembunyikan file berawalan titik), maka command update ini akan menghapus `.gitignore` (risiko: `release.keystore` lokal bisa ikut ter-track/ter-commit ke Git kalau ada di direktori proyek) dan `.github/workflows/build.yml` (CI Actions berhenti berjalan tanpa notifikasi eksplisit — build gagal senyap) — **secara PERMANEN** di working directory Termux, walau riwayatnya masih bisa dipulihkan dari `git log` karena baru ter-commit setelah itu (kalau langkah `git add -A && git commit` di command yang sama tetap jalan, PERUBAHAN PENGHAPUSAN itu justru ikut ter-commit & ter-push, menimpa versi remote yang benar).
    - **Aturan wajib ke depan (permanen, berlaku untuk SEMUA rilis ZIP proyek ini setelah insiden ini):** sebelum `present_files`, AI WAJIB verifikasi eksplisit lewat `unzip -l` bahwa `.gitignore` dan seluruh isi `.github/` ada di dalam ZIP yang akan dikirim — bukan asumsi. Kalau tidak ada, ZIP TIDAK BOLEH dikirim (Release Blocking Rule) sampai dotfile-nya dimasukkan.
    - **Belum diubah (di luar scope insiden ini, hanya dicatat sebagai opsi ke depan):** command Termux "Kotak Update Harian" milik user sendiri (bukan file di repo) bisa dibuat lebih aman dengan menambah pengecualian eksplisit `! -name '.github' ! -name '.gitignore'` selain `.git` sebagai lapisan pertahanan kedua — belum diterapkan karena itu mengubah command milik user di luar repo, perlu konfirmasi eksplisit dulu kalau mau diubah.

Efeknya: membuka `readme.txt` dari ZIP B setelah sebelumnya pernah membuka `readme.txt` dari ZIP A akan menampilkan/menimpa isi milik ZIP A, bukan file baru — kebalikan dari tujuan dedup yang dimaksud (dedup untuk ZIP yang SAMA, bukan mencampur ZIP yang BEDA).

Belum ditambahkan pembersihan eksplisit karena di luar scope permintaan debugging ini.

## Keputusan Arsitektur Utama
- **Penyimpanan:** `java.io.File` langsung ke `filesDir/notes` (internal storage app-specific, tidak perlu permission). **Belum** migrasi ke Storage Access Framework/`Uri` — itu Batch 3, butuh konfirmasi eksplisit dulu karena mengubah `FileUtils`, `TabItem`, `TabManager` hampir menyeluruh.
- **Concurrency:** `Dispatchers.IO.limitedParallelism(1)` khusus untuk write (urutan auto-save terjamin, no race). `Dispatchers.Default.limitedParallelism(1)` khusus untuk regex (isolasi agar pola "meledak" tidak menyita thread pool lain).
- **State persistence:** `rememberSaveable` dengan `Saver` kustom untuk `TabManager` (bukan `ViewModel`/`SavedStateHandle` formal — itu bagian dari Batch 3).
- **Auto-save:** instan per keystroke (bukan debounce timer) — write dilakukan async tapi tetap dipicu tiap karakter berubah.

## Keputusan Ditolak (dengan alasan, jangan diusulkan ulang tanpa alasan baru)
- **Auto-save timer-debounce (3 detik):** ditolak. Auto-save instan async yang sudah ada lebih aman (jendela data-loss lebih kecil) dan tidak membekukan UI — timer hanya akan mengurangi frekuensi tulis dengan trade-off resiko kehilangan data lebih besar.
- **Migrasi SAF/Uri penuh (DocumentFile, folder picker, dst):** ditolak. Premis "scoped storage butuh SAF" tidak berlaku untuk app ini karena penyimpanan sudah `filesDir` (internal, tidak kena scoped storage). Diganti dengan fitur "Buka Dengan" (intent-filter + impor/sinkron Uri) yang benar-benar menjawab kebutuhan user tanpa migrasi arsitektur.
- **Ganti algoritma hash nama file lokal impor eksternal (mis. ke SHA-256):** ditolak (v1.4.2). Risiko tabrakan hash 32-bit saat ini memang ada secara teori, tapi mengganti algoritmanya membuat berkas yang sudah diimpor sebelumnya (nama lokal format lama) tidak lagi ter-mapping ke salinan lokalnya sendiri — duplikat nyata bagi pengguna lama, regresi yang tidak sepadan dengan risiko teoretis yang sangat kecil di praktik.
